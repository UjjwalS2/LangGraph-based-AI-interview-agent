# LLM Evaluation Frameworks and Semantic Caching Architectures

## LLM Evaluation Metrics (Ragas & G-Eval)
1. **Faithfulness / Groundedness**:
   Measures the proportion of claims in the generated answer that can be directly inferred from the retrieved context. Penalizes ungrounded hallucinations:
   $$\text{Faithfulness} = \frac{|\text{Grounded Claims}|}{|\text{Total Claims in Answer}|}$$
2. **Answer Relevance**:
   Measures how directly the generated answer addresses the original question (ignoring ground truth factuality). Often computed by prompting an LLM to generate potential questions from the answer and computing embedding cosine similarity against the user prompt.
3. **Context Precision & Recall**:
   - **Context Precision**: Evaluates whether all ground-truth relevant chunks are ranked at the top of retrieved context.
   - **Context Recall**: Evaluates whether the retrieved context contains all necessary facts to answer the question.
4. **LLM-as-a-Judge Pitfalls**:
   - **Position Bias**: Preference for the first or last response in pairwise evaluations.
   - **Verbosity Bias**: Tendency to favor longer, elaborate responses over concise ones.
   - **Self-Enhancement Bias**: Tendency of models (e.g. GPT-4, Gemini) to score outputs generated by their own family higher.

## Semantic Caching Architecture
Exact-match caching (`cache[raw_query] = answer`) fails frequently in conversational applications because users formulate semantically identical questions with varying phrasing, synonyms, or whitespace.

### How Semantic Caching Works
1. Incoming query $Q$ is embedded via dense encoder (BGE-M3): $v_Q = E(Q)$.
2. Vector similarity search probes the cache vector store:
   $$S = \max_{c \in \text{Cache}} \text{CosineSimilarity}(v_Q, v_c)$$
3. If $S \ge \tau$ (e.g. $\tau = 0.90$), return cached response $\Rightarrow$ **Cache HIT** ($0$ LLM token cost, latency $< 10$ ms).
4. If $S < \tau$, route request to LLM, obtain response, and write $[v_Q, \text{response}, \text{metadata}]$ back to cache $\Rightarrow$ **Cache MISS**.

### Semantic Cache Safety & Partitioning
Semantic proximity alone is insufficient for multi-task applications. To prevent incorrect reuse:
- **Task Isolation**: A question generation request ("Generate a question on XGBoost") must NEVER match an answer evaluation request ("Evaluate answer on XGBoost"), even if query embeddings are close.
- **Difficulty & Role Partitioning**: Requests with different difficulty levels (e.g. `easy` vs `hard`) must be isolated.
- **Context Hashing**: For evaluation tasks, the hash of reference context and candidate answer must match to ensure evaluation validity.
